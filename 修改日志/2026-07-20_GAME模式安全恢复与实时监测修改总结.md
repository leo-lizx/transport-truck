# GAME 模式安全恢复与实时监测修改总结

## 1. 任务范围与结论

本次针对 `MAIN_RUN_MODE_GAME` 静态检查中确认的问题进行修复。根据现场信号约定，保留“上电即发车”，没有增加按键、上位机或串口启动门控。

已修复的四类问题：

1. 合法边界格的误越界判定；
2. 断链恢复后使用掉线前陈旧地图；
3. 看门狗复位后关卡进度丢失、里程计位置无效却盲目续跑；
4. 主循环将积压的 5ms tick 一次清零，且缺少 `Game_Logic_Task_Run()` 实测耗时数据。

代码级判定：修复后的流程与项目内 `规则提炼.md` 中的三关连续执行、最外圈越界终止、死局回发车区静止等要求一致性更高。最终赛规符合性仍需在实车上核验外边界尺寸、视觉 194B 帧和 800us 实时上限。

## 2. 关键改动

### 2.1 越界几何修正

原逻辑把 14×10 可通行内场 `2.8m×2.0m` 当成完整物理场地边界，但里程计坐标原点恰好在该内场左上边界。对车体外接圆使用 `0.175m` 半径和 `0.05m` 滞回后，第 1 列与第 14 列格中心都会被误判越界。

现在显式区分：

- 完整物理场地：`3.2m×2.4m`；
- 可通行内场：`2.8m×2.0m`；
- 在现有里程计坐标系中，物理外边界为 `X=[-0.20,3.00]` 和 `Y=[-0.20,2.20]`。

OOB 改为对完整物理场地做外接圆判定，并删除了仅保护左侧发车的 `s_launch_oob_guard_active` 临时豁免，避免它掩盖真实越界。

几何回归值：

```text
第 1 列车体最左点  = -0.075m，左侧触发线 = -0.25m，不误报
第 14 列车体最右点 =  2.875m，右侧触发线 =  3.05m，不误报
第 1/10 行同理，均在上下触发线内
```

### 2.2 断链恢复改为新鲜地图重规划

原 `recover_from_link_pause()` 在链路恢复后立即冻结 `g_game_map` 并进入 `STAGE_RECOGNIZE_MAP`。掉线若发生在推箱前后，该快照可能仍包含旧箱位，继续规划会产生不可执行航点，甚至导致错推或碰墙。

新增 `STAGE_WAIT_RECOVERY_MAP`：

```text
掉线刹停
  -> 链路恢复时记录帧号栅栏
  -> 收集栅栏后 5 帧完整一致地图
  -> 废弃旧识别映射和旧路径
  -> 重新识别 / 重规划
```

恢复等待中如果再次掉线，之前累计的稳定帧会全部作废，从最近一次恢复后重新计数。恢复图若已无箱子，直接进入 `STAGE_LEVEL_JUDGE`，支持掉线期间刚好完成最后一推的情况。

### 2.3 看门狗安全续赛

使用 SRC GPR9/GPR10 保留两个互补校验字，其中只包含：

- 魔数/版本特征；
- 已完成关数 `0..3`；
- 当前是否已进入关内执行；
- 量化到 1° 的航向。

记录每 100ms 更新，关卡完成时立即更新。如果复位发生在两个 GPR 写操作之间，互补校验会失败，系统转入普通安全启动，不会使用半更新数据。

RTWDOG 复位后：

1. 保持电机停止；
2. 要求一帧复位后新到的、年龄不超过 250ms 的 194B MAP 车辆坐标；
3. 以视觉坐标恢复 x/y，以 GPR 恢复 yaw；
4. 关内复位再等 5 帧稳定地图重规划，关间复位则重定位后返回发车点。

看门狗恢复同时识别 SRC 的通用 WDOG 和 WDOG3 复位位。不保存 BFS 缓冲、解算结果或旧航点，因此不会在复位后依据旧位置盲走。

### 2.4 5ms tick 不再一次清空

原 `wait_for_tick()` 读出 `s_main_tick_pending` 后直接清零，而返回的 tick 数被主循环忽略。屏幕刷新等操作如果超过 5ms，多个业务拍会被实际丢弃。

现在每轮只将 pending 原子递减 1，剩余拍由后续循环追赶。`s_main_tick_overrun` 累计“消费后仍存在积压”的延迟拍数，不再代表被丢弃拍数。

### 2.5 GAME 单拍 DWT 耗时监测

在 `MAIN_RUN_MODE_GAME` 下启用 Cortex-M7 DWT 周期计数器，只包围 `Game_Logic_Task_Run()`，不将 100ms 菜单刷屏计入状态机耗时。IAR Live Watch 可观察：

- `s_game_tick_last_us`：最近一拍耗时；
- `s_game_tick_max_us`：上电后最大耗时；
- `s_game_tick_over_800us`：超过 800us 的拍数。

本次没有在无实测数据时改写求解器分片策略。若实车上 `s_game_tick_over_800us` 增长，再按最大耗时所在 stage 做针对性拆分。

## 4. 内存与实时性影响

- 没有新增大数组；恢复地图稳定表决复用已有的两个 192B 缓冲。
- 新增静态标量约 28B，远低于 10KB BSS 增量限制。
- 正式 GAME 编译链接图显示 `77,482 bytes of readwrite data memory`，低于项目 SRAM 预算。
- 日常运行时每 100ms 额外写两个 SRC GPR；断链/看门狗恢复期才进行 192B 地图稳定比较。
- DWT 记录已经加入，但 800us 约束必须以实车运行的 `s_game_tick_max_us` 和 `s_game_tick_over_800us` 最终判定。

## 6. 实车验证项与限制

1. 正式赛前切换到 `MAIN_RUN_MODE_GAME`，观察 `s_game_tick_max_us` 与 `s_game_tick_over_800us`。
2. 分别在识别、规划和推箱中途断开 OpenART1/OpenART2，确认停车后至少收到 5 帧新图才继续。
3. 人为停止喂狗验证 RTWDOG 复位原因和 GPR 保留；若视觉端只发 192B 地图、不发 194B 车位图，看门狗恢复会按设计保持停车，不会盲走。
4. 以实际场地测量复核 `3.2m×2.4m`、每格 `0.20m` 和外边界滞回值；若现场场地版本不同，只调整 `CHASSIS_FIELD_*` 硬件契约宏。
