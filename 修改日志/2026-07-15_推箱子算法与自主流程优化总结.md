# 推箱子算法与自主流程优化总结

## 1. 任务目标与结论

本次工作围绕“车辆从发车区自主连续完成三关、不同航向均能到达实际目标点、推箱与识别流程结合延迟视觉进行校准”完成实现和验证。

最终方案采用：

- 修正底盘车体系与地图全局系的变换符号，覆盖 `0° / 90° / 180° / -90°` 四个基准航向；
- 网格航点派发时把残留斜角吸附到最近的 90° 倍数；
- Stage2 按 BFS 实际绕障距离选择下一只箱子，并与 PC 镜像同步；
- 关间静止窗口和识别最终观察点使用事件驱动视觉 Snap，不开启默认连续融合；
- 正式比赛入口运行三关状态机，成功关和按死局流程结束的失败关都计入三关；
- 修复识别状态机被预处理宏整体屏蔽的问题，确保识别代码真正编译、链接并运行。

## 2. 关键改动

### 2.1 四航向坐标变换修复

地图全局系为 `X 向右、Y 向下`，车体系为 `X 向右、Y 向前`。结合“发车航向 180° 时车头朝地图 -Y”和识别朝向公式 `yaw = atan2(dx, dy)`，车体速度到全局速度的正确变换为：

```text
global_x =  cos(yaw) * body_x + sin(yaw) * body_y
global_y = -sin(yaw) * body_x + cos(yaw) * body_y
```

已在 `chassis_ctrl.c` 同步修正：

- 里程计位置积分；
- 位置环 D 项的全局速度测量；
- POINT_NAV 全局速度到车体速度的逆变换；
- `chassis_ctrl_get_odom_velocity_global_mps()`。

`chassis_zone.c` 原有软限位已经使用同一正确约定，无需修改。

### 2.2 航向吸附

在 `chassis_config.h` 增加 `chassis_snap_yaw_to_cardinal_deg()`，把任意航向吸附到最近的 `0° / ±90° / 180°`。推箱航点和识别巡航航点派发时均使用该函数，避免识别采样后的任意斜角继续影响轴对齐网格移动。

### 2.3 Stage2 绕障选箱

Stage2 原先按曼哈顿距离选择下一只箱子，遇到墙体或其他箱子阻挡时，可能优先选择“直线近但实际绕路远”甚至暂不可接近的箱子。

现在每轮从玩家当前位置执行一次 192 格 BFS 洪泛，再按箱子四邻接可站立格的最短实际距离选箱；不可接近的箱子不会被误选。C 端和 `pc_sokoban/sokoban_validator.py` 已保持一致。

Stage1/Stage2 串行复用同一份 `sb_nav_distance[12][16]`，没有为 Stage2 额外增加 192B BSS。

### 2.4 视觉校准策略

保留“运动中以里程计为主、关键静止点用视觉校准”的策略：

- 发车前：地图稳定后，车辆在发车区静止，使用现有多帧 Snap 对视觉格坐标表决，再将航向校准为 180°；
- 识别巡航：中间转弯航点只用里程计到位，最终观察航点才执行视觉 Snap，随后按校准后的实际位姿计算面向物体的 yaw；
- 推箱执行：继续使用已有的每航点到站 Snap；
- 视觉无有效结果：Snap 内部 800ms 超时，关间另有 2s 上层兜底，均会回退到里程计并放行，不会卡死状态机；
- 连续视觉融合仍保持默认关闭，避免整数格量化噪声在运动中持续注入控制环。

### 2.5 三关自主流程

`project/user/src/main.c` 已从第二关单测模式切换为 `MAIN_RUN_MODE_GAME`，正式入口会周期调用 `Game_Logic_Task_Run()`。

三关流程现在为：

```text
WAIT_START 回发车区 / 等稳定地图 / 视觉校准 / 自动驶出
  -> RECOGNIZE_MAP 遍历并识别箱子与目标
  -> PLAN_PATH 推箱或炸弹规划
  -> EXECUTE_ACTION 执行航点
  -> LEVEL_JUDGE
     -> 未满三关：回 WAIT_START
     -> 已满三关：STAGE_DONE
```

失败流程为：

```text
规划失败或执行两次超时
  -> DEADLOCK_RESET
  -> 按当前左/右发车区返回
  -> 发车区内静止满 3s
  -> 本关计入已结束关卡数
  -> 下一关或三关结束收车
```

这避免了原逻辑永远等待第四张地图，也修复了右发车区失败回位仍写死左侧起点的问题。

### 2.6 识别实现重新接入构建

`app_recognize_clear.h` 中残留的 `APP_RECOGNIZE_USE_CLEAR` 会使 `app_recognize.c` 主体被 `#ifndef` 整体排除，IAR 链接曾报以下三个未定义符号：

- `App_Recognize_Reset`；
- `App_Recognize_Tick`；
- `App_Recognize_Get_Debug`。

已删除失效的屏蔽宏和对应条件编译外壳。最终链接映射中已确认 `App_Recognize_Tick` 和 `Game_Logic_Task_Run` 均进入固件镜像。

## 5. 实时性与已知限制

- 新增的关间/识别 Snap 每个 5ms tick 只执行常数级状态检查；识别中只在最终观察航点等待，不放大每个中间航点耗时。
- Stage2 每只箱子新增一次 192 格 BFS，仅在 `PLAN_PATH` 规划阶段执行，不进入底盘 20ms 闭环或 ISR。
- IAR 构建和 PC 流程均已完成，但当前环境没有连接 RT1064 实车、全局视觉和比赛软件，因此无法替代以下现场验收：
  1. 四个基准 yaw 下各执行一次单格移动，核对真实位移方向；
  2. 观察 `s_main_tick_max_us`，确认实车最坏 `Game_Logic_Task_Run` 仍小于 800µs；
  3. 采集视觉帧延迟及 `snap_done / snap_timeout / snap_reject` 比例；
  4. 实跑“三关全成功”和“中间一关失败后静止 3s 继续”两条完整比赛流程。
